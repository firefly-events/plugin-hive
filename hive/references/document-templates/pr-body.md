# PR body template — autonomous worker output

Used by `.sandcastle/prompts/worker-issue-pickup.md` and any other agent that
ships a PR through Hive. The goal: reviewers should not have to read the diff
to know what changed, why, and how it was verified.

## Template

```markdown
## Summary

<1-2 sentences: what this PR does and the user-visible / system-visible
reason it exists. Lead with the "why", not the "what" — well-named files
already say what.>

Closes #<N>. Story: `<story-id>` (epic `<epic-id>`).

## Touch points

<One bullet per file. Path in backticks, then dash, then a one-line "what
changed" — not just "modified" or "updated". Group new files separately
from edits if the list is long.>

- `path/to/new-file.ext` — **NEW** — <purpose, e.g. "Zod schema for the
  worker result shape">
- `path/to/edited.ext` — <what changed, e.g. "thread `gate_mode` through
  the dispatcher so warning paths surface telemetry">

## Acceptance criteria coverage

<Table mapping each AC from the story spec to the surface that implements it.
If an AC is partially covered or deferred, say so explicitly — don't elide.>

| AC | Surface |
|---|---|
| <one-line AC paraphrase> | `<file>:<line>` or `<test file>` |
| <next AC> | <surface> |

## Verification

<What was actually run, with results. NOT "tests pass" — name the suite, name
the count, name the slow/skipped ones. If a check couldn't run in this
environment, say WHY explicitly so reviewers don't assume it was covered.>

- `node --test tests/<file>` — N passed, 0 failed
- `eslint <path>` — clean
- <manual check>: <what was tried, what was observed>

If automated verification was incomplete:

- **Not run here:** <suite name> — <reason, e.g. "requires PyYAML inside
  sandcastle container; CI will run it on merge">

## Risks / followups

<Real risks the reviewer should weigh. Skip this section if there are none —
do not write "no risks identified" filler. Use bullets, one risk per line,
each with severity and a mitigation or followup link.>

- **medium** — <risk>. Mitigation: <what was done> / Followup: <issue #
  or "needs triage">.

## Notes for the reviewer

<Only when there's something non-obvious: a design decision that looks
wrong-at-first, a deferred refactor with rationale, a known-but-accepted
trade-off. If everything is obvious from the diff + above sections,
delete this section.>

---

Generated by sandcastle-ops autonomous worker.
```

## Rules

1. **Always include `Closes #<N>`** so GitHub auto-closes on merge.
2. **Lead Summary with the WHY**, not a restatement of the title.
3. **Touch points must be specific.** "Updated config" is useless — say what
   changed and why.
4. **AC coverage is mandatory** when the story has `acceptance_criteria`.
   If a story has none, omit the section.
5. **Verification names what ran, not what passed.** "All green" is
   reviewer-poison — list the suite, the count, the env.
6. **No filler sections.** If risks/notes have nothing to say, delete the
   heading entirely. Empty section = wasted attention.
7. **Skip drift.** If the implementation diverged from the story spec
   (different approach, scope expansion, scope cut), call it out in
   Summary or Notes. Reviewers catch drift faster when authors flag it.
