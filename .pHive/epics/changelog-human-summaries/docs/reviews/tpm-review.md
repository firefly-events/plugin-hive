**Position on U1 (ghost-risk investigation as story 1 with explicit branch decision): YES — and the evidence makes it stronger than the grill states.**
I grepped CHANGELOG.md for the step 7e template line ("release finalization"): zero occurrences across the entire committed history. The step 7e line has never landed in CHANGELOG.md. Either step 7e never fires in the normal flow, or its output is always replaced before commit. This means the High risk in design §4 is not hypothetical — it is prima facie confirmed. The plan MUST structure story 1 as the investigation with an explicit three-way branch decision recorded as its output: (a) extend step 7e, (b) move authoring to chore(release) guidance, (c) add a new dedicated authoring step in /execute before 7e. Stories 2+ for the authoring change should be written against the branch outcome, not against a pre-committed 7e callsite. Do not bake "extend step 7e" into story titles or acceptance criteria before story 1 closes. Sequencing-wise this is cheap: story 1 is a half-day investigation (git log archaeology + one /execute trace), and it de-risks every downstream story. This is exactly the debuggability pattern we want — if the authoring change misfires, we know it's the callsite choice, not five stacked unknowns.

**Position on H1 (fallback when story outcome data is absent at step 7e): adopt the release_post.mjs fallback chain as the spec; never block, never hallucinate.**
`hive/lib/release_post.mjs:81-99` already solves this exact problem with a graceful degradation chain: `outcome ?? description_summary ?? firstSentence(description) ?? title`. I also checked story YAMLs across existing epics: no story carries a top-level `outcome:` field today (the only `outcome:` hits are metric-block PASS/FAIL values, a different field entirely). So the "outcome absent at 7e" case is not an edge case — it is the CURRENT NORMAL case. The fallback is therefore not optional hardening; it is the primary path on day one. The authoring instruction must specify: draft each bullet from `outcome` if present, else from story title + first sentence of description, and mark the entry as degraded-source in the draft (e.g. an HTML comment) so the operator review knows which bullets were synthesized from thin data. Blocking at 7e is wrong (it would dead-stop every current epic), and deferring authoring to ship-time is wrong (ship is a gate, not an author — design §2 already establishes this). One sequencing consequence: if the team wants richer bullets long-term, "populate story outcome at integrate time" is a separate, deferrable follow-up story — defer it explicitly, do not let it creep into this epic.

**Position on V1 (commit to Small or Medium): Small. The investigation does not tip it.**
The worst-case branch outcome (7e is a ghost, authoring moves to a new /execute step or chore(release) guidance) is still 2-3 skill-file prose edits plus one reference doc. No migrations, no code, no cross-team coordination, no new subsystem. The investigation is a bounded story INSIDE a Small plan, not a scale escalator — its output changes WHERE the prose lands, not HOW MUCH work exists. Routing this through Medium H/V planning would add overhead without adding clarity, which the design's own §8 rationale already concedes. SCALE DECISION: Small.
