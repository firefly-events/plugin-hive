# Security Plan Audit — hive-dag-executor

**Date:** 2026-05-01T23:26:08Z
**Reviewer:** security-reviewer (Claude)
**Branch:** feat/hive-dag-executor-foundation
**Workflow contract:** hive/workflows/security-audit.workflow.yaml

## Findings

- `hde-8 / hive/lib/dag_executor/pause/token.py` — Resume-token signing scheme is described as `run_id + node_id + timestamp + signature` but the **signing-key source is not specified anywhere in the plan** (epic.yaml, structured-outline §Phase 3 / Changes #2, horizontal-plan L3 pause module tree, design-discussion §4). Without an explicit, audited key-sourcing decision, a maintainer could implement (a) a hard-coded constant — token forgery is trivial; (b) a per-machine random key in `~/.config/...` — fine on single host, breaks cross-host resume; (c) per-run derived from `run_id` — equivalent to no signature at all because `run_id` is also in the token payload. [severity: major]
  - **Mitigation:** Add an explicit "Signing key sourcing" subsection to hde-8's design decisions and to `hive/references/workflow-schema.md` pause section. Lock to: per-run secret generated at `run_state.create()`, stored at `.pHive/runs/{run_id}/.signing_key` with mode `0600`, never logged, never leaves the machine. Add `test_token.py` cases that verify (i) tampered payload is rejected, (ii) token from run-A cannot resume run-B (cross-run forgery), (iii) signing-key file mode is `0600` after creation, (iv) signing key is never present in `run_state.yaml` or telemetry events.

- `hde-8 / hive/lib/dag_executor/pause/signal.py` — File-sentinel external signal at `.pHive/runs/{run_id}/pause/{node_id}.{approve|reject}` has **no documented atomicity, permission, or write-authorization model** (structured-outline §Phase 3 / Changes #3 only mentions "orphaned pause files must not resume the wrong node" and "timeout policy must be explicit if configured"). On a multi-user host or a CI runner with shared scratch, any process that can write to `.pHive/runs/` can forge an approval. The plan does not specify: (a) directory mode for `.pHive/runs/{run_id}/pause/`, (b) file-creation atomicity (write+rename vs direct write — partial-write races could be read mid-write), (c) any binding between the sentinel file and the resume token (the sentinel is just a filename, the token from token.py is unused at signal-verification time). [severity: major]
  - **Mitigation:** Sentinel file MUST contain the resume token in its body, and `signal.py` MUST verify the token's signature before honoring approve/reject. This binds the sentinel to the issued token and defeats both forgery and replay (token includes timestamp). Lock directory mode to `0700` on creation. Use `os.open(..., O_CREAT | O_EXCL, 0o600)` + `os.rename()` for atomic publish. Add `test_signal.py` cases for: (i) sentinel without valid token rejected, (ii) sentinel with token from different run_id rejected, (iii) sentinel containing token from a *different node_id* in the same run rejected, (iv) directory perms `0700` enforced.

- `hde-8 / pause polling cadence` — `signal.py` documents "polling cadence + timeout (max wait configurable, defaults to no-timeout for human-gated)" (horizontal-plan L3 pause module). A **default of "no timeout"** combined with file-based polling means a forgotten pause node holds an open run-state, an open worktree, and an open run-id forever. While not strictly a confidentiality/integrity hole, it is a denial-of-service and stale-token surface — a token that lives forever can be re-used by an attacker who later gains filesystem access. [severity: moderate]
  - **Mitigation:** Add a hard ceiling default (e.g., 30 days) above which the run terminates with `PauseTimeoutError`, even when the user-facing default reads as "no timeout." Document this in `hive/references/workflow-schema.md` as a security floor, not a UX default.

- `hde-9a / .pHive/hive.config.yaml` triple-defense — The plan (epic.yaml risk #6, vertical-plan §Step 5) lists the defenses as "(a) config layer split, (b) **optional** CI guard, (c) explicit citation in hde-9a design decisions." The word **optional** on (b) is the failure mode. eefbff3 happened *because* there was no CI guard at all; making the second leg of a triple-defense optional means, in practice, you have a double-defense — the same shape that already failed once. The verification-strategy section (§7) says "CI guard (if practical)" which is the same softening. [severity: major]
  - **Mitigation:** Promote the CI guard from "optional" / "if practical" to **mandatory** before hde-9a ships. Implementation: a `tests/test_shipped_config_no_executor_flag.py` or a pre-commit hook that fails if `hive/hive.config.yaml` (the shipped maintainer-side config) contains any `executor:` key under any path. The check is ~10 lines and has no dependency footprint. Update epic.yaml risk #6 mitigation and structured-outline Decision Point 5 to remove the "optional" hedge.

- `hde-7 / hive/lib/dag_executor/executor/tool_gating.py` — `pure_override_with_surface_when_overrides` policy (cycle-state user-gate lock) is correctly designed for *auditability* (emits `tool_gating_overridden` audit event on every override per horizontal-plan L2) but the audit event is the **only** check on a step-level escalation. There is no second factor — no allow-list of which steps are permitted to escalate, no signed-step-author concept, no review-gate on workflow YAMLs that introduce step-level `tools:` overrides. A workflow YAML edit that adds `tools: [Bash, Write]` to a node bound to a `researcher` persona (which only has Grep/Glob/Read) silently grants those tools, with the audit event the only post-hoc trace. [severity: moderate]
  - **Mitigation:** Two layers — both cheap. (1) `tool_gating.py` MUST refuse to grant any tool not present in a maintainer-controlled `hive/lib/dag_executor/executor/escalatable_tools.yaml` allow-list. Tools like `Bash`, `Write`, `Edit` should require explicit allow-list entry; tools like `Grep`/`Glob`/`Read` are always grantable. This converts a silent override into a hard failure unless the maintainer pre-approved the tool as escalatable. (2) Record both the persona-baseline tool set and the effective tool set in the audit event payload (not just "overridden: yes") so a downstream meta-review can detect privilege drift.

- `hde-7 / codex tool gating` — Risk #11 covers `PlatformIncompatibilityError` for non-Darwin (good) but does NOT cover the case where a workflow YAML adds `tools: [codex]` to a step bound to a persona that should not run external models (e.g., `reviewer` is pinned to Opus precisely so it can cross-verify Codex output per `feedback_codex_general_backend`). A step-level `tools: [codex]` override on `reviewer` would silently re-route the verifier through the same backend it's meant to verify. [severity: moderate]
  - **Mitigation:** Add `codex` and `cmux` to the escalatable_tools.yaml allow-list (proposed above) **with a per-persona deny-list**: list of personas (`reviewer`, `peer-validator`, `security-reviewer`) for which `codex` may NOT be granted via step-level override even if the tool is generally escalatable. `tool_gating.py` raises `BackendIsolationViolationError` on attempted escalation. `test_tool_gating.py` covers the deny-list path.

- `hde-5 / hive/lib/dag_executor/run_state/store.py` resume primitives — Narrow-mutation API (`create / load / set_node_status / set_node_output / append_event / freeze`) is good for write-time TOCTOU; `schema_version: 0` pinning protects against version skew. But `resume.py` (`--resume <run-id>`) walks `.pHive/runs/{run_id}/run_state.yaml` from CLI input. The plan does not document: (a) `run_id` input validation (an attacker-controlled `run_id` of `../../../etc` traverses outside `.pHive/runs/`), (b) ownership check on the resume target (a run started by another process/user could be hijacked on shared hosts), (c) freeze-after-completion enforcement (can a completed `run_state.yaml` be unfrozen and re-resumed?). [severity: moderate]
  - **Mitigation:** `resume.py` MUST validate `run_id` against the documented format (ULID-shaped per hde-2 `run_id.py` — already locked) before composing any path. Reject any `run_id` containing `/`, `..`, or non-ULID characters. Add `test_resume.py` cases for path-traversal `run_id` rejection, and assert that `freeze()` makes `run_state.yaml` immutable to subsequent `set_*` calls (RuntimeError, not silent no-op).

- `hde-6 / hive/lib/dag_executor/isolation/worktree.py` — Worktree-per-run is at `.pHive/runs/{run_id}/`. The plan covers nesting/collision (good — `nesting.py` + `test_nesting.py`) but does NOT address **symlink or absolute-path escape from within step execution**. A malicious step (or a misbehaving Codex-backend agent) could write to `/Users/...` or follow an attacker-planted symlink at `.pHive/runs/{run_id}/something -> ../../hive/hive.config.yaml` to mutate maintainer-side config from inside a "contained" worktree. The git worktree itself does not provide filesystem isolation — only branch isolation. [severity: moderate]
  - **Mitigation:** Document the trust boundary explicitly in `hive/references/cycle-state-schema.md` ownership-split section: worktree-per-run isolates **branch state**, NOT filesystem writes. Step handlers that delegate to external processes (codex, dev classic Bash) should set `cwd` to the worktree but MUST NOT assume the process is jailed there. As a defensive layer, `worktree.py.create()` should refuse to proceed if `.pHive/runs/{run_id}/` already contains a symlink (created out-of-band) — fail with `WorktreeContaminationError`.

- `hde-3a / hive/lib/dag_executor/predicate/parser.py` — Strict Archon grammar lock with triple-defense (parser rejects regex/status-functions/parens/arithmetic; predicate-grammar.md cultural lock; reviewer practice rejects expansion) is **strong**. Single residual gap: the plan does not specify that `$`-prefixed accessors are evaluated against a **closed set of fields** (presumably `cycle_state.*` and `step.*.outputs.*`) and not against arbitrary Python attribute access. If `$step.foo.outputs.bar` resolves via `getattr` chains, an `output_format` JSON field named `__class__` or `__init__` becomes a code-eval surface. [severity: minor]
  - **Mitigation:** `predicate/evaluator.py` accessor resolution MUST use dict `.get()`-style lookup, not `getattr`. `test_predicate_grammar.py` adds cases for `$step.foo.__class__`, `$cycle_state.__init__`, and similar dunder-access patterns being rejected at parse time (reserved name) or returning `None` at eval time (never traversing).

- `hde-9b / .pHive/runtime/executor-graduated-workflows.yaml` — The graduation registry is correctly maintainer-controlled and lives outside shipped config. Plan does not document (a) who can write to it, (b) whether it is signed/checksummed, (c) whether `hde-9a` config-layer split refuses to honor a registry entry that mismatches a hash in shipped code. Lower urgency than the hde-9a triple-defense gap because `executor-graduated-workflows.yaml` lives in `.pHive/` (consumer-side already), not in shipped code. [severity: minor]
  - **Mitigation:** Document in hde-9b that the registry is consumer-controlled and intentionally trusts the local maintainer. No additional defense needed if hde-9a's CI guard (above) is mandatory.

## Threat Model Notes

- **Trust boundary for executor runs:** local-machine maintainer + their tooling only. The plan correctly does not add network endpoints, cross-host RPC, or remote-attestation surfaces. No new external attack surface.
- **New IPC channel introduced:** file-sentinel pause/approve at `.pHive/runs/{run_id}/pause/{node_id}.{approve|reject}`. This is the **only** new attacker-influenceable input introduced by the initiative; it deserves the most defense (findings #2 and #3 above).
- **Worktree boundary:** isolates branch state, NOT filesystem writes. A step handler escapes the worktree the moment it `os.chdir` or `open(absolute_path)`. This is a documentation gap, not a fixable design flaw — git worktrees are not jails.
- **Codex-backend trust:** `feedback_codex_general_backend` separates work-producing personas (Codex) from verifier personas (Opus). The tool-gating composition policy can silently violate this separation if a workflow YAML adds `tools: [codex]` to a verifier-step (finding #6). The audit event traces the violation, but a second factor (allow-list with per-persona deny-list) is cheap insurance.
- **Predicate evaluator:** strict-Archon lock + triple-defense is the right shape; only residual concern is accessor resolution semantics (finding #8). Argo issues #6823 / #7089 are correctly cited as the cautionary tale.
- **run_state schema:** narrow-mutation API + schema_version pinning is correct. Resume primitives need `run_id` validation (finding #7) but the underlying mutation API is sound.

## Specific Concerns Resolved (cycle-state escalations[1].reason)

- **Per-node tool gating composition:** **Approved with required revision.** The `pure_override_with_surface_when_overrides` policy is auditable (the `tool_gating_overridden` event is emitted on every override per horizontal-plan L2), and "deny-wins" / "union" / "intersect" alternatives were correctly rejected — they collapse the per-step expressivity that workflow authors need. **However**, "pure override" by definition allows step-level YAML to grant a tool the persona disallows, with the audit event as the only check. This is acceptable for low-blast tools (Grep/Read) but unacceptable for high-blast tools (Bash, Write, Edit, codex, cmux). Required revision: add a maintainer-controlled `escalatable_tools.yaml` allow-list and a per-persona deny-list for verifier-isolated backends (finding #6 above). With that revision, the composition policy is sound and the audit trail is sufficient.

- **Config-flag location precedent (eefbff3):** **Approved with required revision.** Q4 lock to consumer-side `.pHive/hive.config.yaml` default OFF is the correct shape and directly addresses the eefbff3 / `project_config_shipping_deferred` precedent (where maintainer-only Codex/Opus defaults accidentally landed in shipped `hive/hive.config.yaml` — exactly the failure pattern this initiative must avoid). Triple defense (config layer split + CI guard + explicit citation) is the right structure. **However**, the CI guard is documented as "optional" (epic.yaml risk #6) and "if practical" (design-discussion §7) — eefbff3 happened *precisely because* there was no CI guard at all, and an "optional" leg of a triple-defense reduces it to a double-defense identical in shape to the one that already failed. Required revision: promote CI guard to mandatory (finding #4 above) — the implementation is ~10 lines (a pytest that asserts no `executor:` key in shipped `hive/hive.config.yaml`) with no dependency cost. With that revision, the triple-defense is sufficient and the eefbff3 risk is closed.

## Summary

The hive-dag-executor initiative plan is, at the architecture level, **security-sound**: the strict-Archon predicate grammar with triple-lock defense correctly heads off the Argo-style hidden-orchestration risk; the worktree-per-run + run_state schema-versioning + nesting policy correctly isolate run state; and the user-gate decisions on consumer-side config and pure-override tool gating are the right calls. The two architect/tpm escalation concerns are both genuinely addressed in the plan, but one ("optional" CI guard for hde-9a) softens the eefbff3 mitigation enough to be a major finding, and one (no second factor on tool-gating override) needs an allow-list to prevent silent verifier-persona escalation. Two additional major findings surfaced from the standard plan-audit lens — both on hde-8: the resume-token signing-key source is undocumented, and the file-sentinel signal channel has no token-binding or atomicity model. All four major findings have small, concrete, low-cost mitigations; none require redesign. Six moderate/minor findings round out the standard hardening checklist. The initiative can begin dispatch after the four major findings are resolved at the corresponding story-spec level (hde-7, hde-8, hde-9a) — none of them gate Slice 1 (graph + executor skeleton) on disk, so the prep PR can land while these are addressed in story specs before the relevant slices begin.
