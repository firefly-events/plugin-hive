# Insights — sdr-10-executable-prose-conversion

- The story's audit regex (`rg -nP '(mkdir|cp|cat|tee|cat\s*>|>)\s+\.pHive'`) only catches shell-op forms. Prose-form executable instructions ("Read the current baseline at `.pHive/...`", "Results MUST be written to `.pHive/...`") are invisible to it. When auditing, follow the regex hits to their files and then sweep ALL `.pHive` refs in those files — most are executable prose the regex missed.
- step-04/05/07 of test-swarm (inspector/sentinel/report) also contain prose-form `.pHive` read instructions but match neither the audit regex nor the story's named files; deliberately left literal per the "found by the audit" scoping. A follow-up story is needed if those should honor `paths.state_dir` too — note they receive paths from step-03's results.yaml, which now records `${HIVE_STATE_DIR}` template paths, so downstream steps consume the resolved values at runtime.
- Two conversion conventions coexist in the repo: skills get a `## State Directory Resolution` section (skills/ship, skills/execute), workflow step files get a one-line header blockquote (`> $HIVE_STATE_DIR resolves from paths.state_dir...`, see meta-team-cycle steps). Followed both; don't invent a third.
- YAML templates inside step files (results.yaml schema, episode markers) were converted too: agents fill those templates with real paths, so leaving `.pHive` there would make recorded artifact paths wrong under a custom state dir. They are templates of runtime values, not illustrative examples.
- `__tests__/step-04b-scenario-replay.test.mjs` embeds literal `.pHive` paths in its own fixture data — it does not parse the step markdown, so it is unaffected and intentionally untouched.
